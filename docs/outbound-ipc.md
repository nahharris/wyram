# Outbound IPC

Issue #5 removes JSON serialization, stdout writes and flushes from native input/redraw callbacks. The engine and the four-byte big-endian length + JSON protocol remain unchanged. A single worker owns outbound I/O. There are no new dependencies or gameplay rules in Rust.

The queue holds at most 128 pending edits, one pending sequenced character input, one capabilities announcement and one coalesced scenery credit, plus one packet being written. Edit admission preserves FIFO order and never replaces an edit. Newer character input removes the previous pending input and appends at its own submission position; input already being written cannot be replaced. This skips obsolete held-key states without reordering retained packets. Changes are sent on the next frame, with 100 ms heartbeats. The client no longer sends authoritative positions.

The queue uses one mutex and condition variable. Producers never wait for queue space. Producers and writer hold the mutex only for bounded queue/counter operations; serialization, I/O, error reporting and condition-variable waits happen outside that critical section. Queue access can briefly contend with another thread and is not a hard real-time guarantee. Queue storage is preallocated, packet fields are fixed-size, and coalescing examines at most 131 entries.

A single ordered queue avoids the merge/ordering policy required by separate input and edit channels. An unbounded channel would move the stall into memory growth; waiting for space would restore the original renderer stall. Ending a saturated session gives an explicit outcome without introducing a new rejected-edit UI or replay protocol. Capacity 128 is a finite backlog limit, not a throughput target; change it only with workload evidence.

If a new edit would exceed capacity, admission returns `Full`; the client ends the session at the next event-loop wait and prints a diagnostic after leaving the loop. A write/flush failure clears pending packets, closes admission, reports the error on the worker, and sends a disconnect event. This avoids silent edit loss during continued play. There is no engine acknowledgement: successful flush means bytes reached the OS, not that gameplay applied the edit. Pending edits may be undelivered after failure, saturation or application shutdown.

Dropping the outbound owner requests a drain and wakes an idle worker. The background reader holds a scenery-credit handle that does not own shutdown; dropping that handle leaves the owner usable, and owner shutdown closes admission for every handle. The renderer never joins the worker, because an OS pipe write can remain blocked indefinitely. Tests with a functioning receiver join explicitly and assert exact output; production process exit terminates any remaining worker. This bounds shutdown waiting but cannot guarantee delivery on close. A gameplay edit acknowledgement/reconnect protocol would be separate work.

Frame captures expose queue depth, cumulative successfully flushed packets, cumulative replaced inputs, and lifetime maximum queue age and serialization/write/flush duration. The maxima are diagnostics, not per-frame times or latency distributions. The snapshot excludes the in-progress packet. Capture and the performance report remain compatible with older records.

Verification includes a gated receiver proving admission finishes before the blocked write is released, capacity/reserved-input behavior, edit FIFO and latest-input framing, one failure notification with subsequent rejection, real Windows anonymous-pipe round-trip bytes with a delayed receiver, and a real closed pipe. An ignored benchmark alternates synchronous and asynchronous admission on identical ordered edits with a 2 ms delay per flush. It asserts delivery count/order and records producer and complete-drain timings separately; no hardware-dependent timing thresholds run in CI.

Sequenced movement input uses one latest-state slot in the ordered queue. The blocked-receiver test floods input and checks latest sequence/running state, edit order and the 129-packet pending bound. Captures add `outbound_coalesced_inputs`; the legacy `outbound_coalesced_poses` field remains present with zero for compatibility.

Scenery credits describe validated admission to the bounded inbound queue, before UI acceptance or meshing. They cannot displace retained edits or input, and older epoch/delivery pairs cannot replace newer pending credit. See [scenery delivery](distant-scenery-runtime.md#edits-and-delivery) for validation, queue backpressure and failure behavior.
