# Outbound IPC

Issue #5 removes JSON serialization, stdout writes and flushes from native input/redraw callbacks. The engine and the four-byte big-endian length + JSON protocol remain unchanged. A single worker owns outbound I/O. There are no new dependencies or gameplay rules in Rust.

The queue holds at most 128 pending edits and one pending player pose, plus one packet being written. Edit admission preserves FIFO order and never replaces an edit. A newer pose removes the previous pending pose and appends at its own submission position; the pose already being written cannot be replaced. This skips obsolete views under backpressure without reordering retained packets. The renderer still reports at the existing 200 ms interval or on crossing a chunk boundary.

The queue uses one mutex and condition variable. The producer never waits for queue space. Both sides hold the mutex only for bounded queue/counter operations; serialization, I/O, error reporting and condition-variable waits happen outside that critical section. Queue access can briefly contend with another thread and is not a hard real-time guarantee. Queue storage is preallocated, packet fields are fixed-size, and removing a pose examines at most 129 entries.

A single ordered queue avoids the merge/ordering policy required by separate pose and edit channels. An unbounded channel would move the stall into memory growth; waiting for space would restore the original renderer stall. Ending a saturated session gives an explicit outcome without introducing a new rejected-edit UI or replay protocol. Capacity 128 is a finite backlog limit, not a throughput target; change it only with workload evidence.

If a new edit would exceed capacity, admission returns `Full`; the client ends the session at the next event-loop wait and prints a diagnostic after leaving the loop. A write/flush failure clears pending packets, closes admission, reports the error on the worker, and sends a disconnect event. This avoids silent edit loss during continued play. There is no engine acknowledgement: successful flush means bytes reached the OS, not that gameplay applied the edit. Pending edits may be undelivered after failure, saturation or application shutdown.

Dropping the producer requests a drain and wakes an idle worker. The renderer never joins the worker, because an OS pipe write can remain blocked indefinitely. Tests with a functioning receiver join explicitly and assert exact output; production process exit terminates any remaining worker. This bounds shutdown waiting but cannot guarantee delivery on close. A delivery acknowledgement/reconnect protocol would be separate work.

Frame captures expose queue depth, cumulative successfully flushed packets, cumulative replaced poses, and lifetime maximum queue age and serialization/write/flush duration. The maxima are diagnostics, not per-frame times or latency distributions. The snapshot excludes the in-progress packet. Capture and the performance report remain compatible with older records.

Verification includes a gated receiver proving admission finishes before the blocked write is released, capacity/reserved-pose behavior, edit FIFO and latest-pose framing, one failure notification with subsequent rejection, real Windows anonymous-pipe round-trip bytes with a delayed receiver, and a real closed pipe. An ignored benchmark alternates synchronous and asynchronous admission on identical ordered edits with a 2 ms delay per flush. It asserts delivery count/order and records producer and complete-drain timings separately; no hardware-dependent timing thresholds run in CI.
