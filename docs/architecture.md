# Architecture

The engine is an Elixir umbrella. `wyram_plugin_api` declares the public plugin contract; `wyram_engine` owns startup, plugin registration, the world and the native-client port. The Wyram game is a separate compiled plugin. Native code is a Cargo workspace: `wyram_core` contains packed 16³ voxel chunks and deterministic terrain, `wyram_nif` exposes batch operations to Elixir, and `wyram_client` owns the winit window and wgpu renderer.

Each region GenServer owns the packed chunks in a 4 by 4 chunk-column area. World operations route directly to the region process through a Registry; the World GenServer serializes durable edits to the save file. Regions load edited chunks when they start, so a crashed region can recover from the saved state. The client receives chunk snapshots through a length-prefixed JSON port protocol, keeps a visual replica, and sends edit intents. Native terrain generation is a dirty CPU NIF; rendering is outside the BEAM VM.

Current limitations are deliberate and measurable: initial streaming is synchronous; targeting remains local and edit validation is minimal; the World save writer still serializes all edits and rewrites the edited-chunk snapshot on every edit; compiled plugins load at startup only. These are the next performance and integrity boundaries to address before claiming the targets in the plan.

The opt-in local control socket lets trusted scripts inspect world blocks and issue validated edits through the engine. The Rust client sends sequenced movement intent asynchronously. A shared Elixir character owner advances fixed 20 ms steps, obtains region-owned chunk snapshots in batches, and resolves packed native sweeps. Character snapshots carry sequence, accepted input sequence and epoch; native prediction samples approved velocity for at most 40 ms and reconciles to those snapshots. Teleports validate destination clearance and advance the epoch, without waiting on an Elixir call in the render loop.

The native renderer keeps separate GPU meshes per chunk. Two bounded workers mesh immutable snapshots of a chunk and its six neighbors; arrivals, edits, palette changes and removals invalidate affected meshes. Monotonic generations reject obsolete results, including after unload/reload. The frame thread drains ready results without waiting, applies a bounded number of uploads, and continues drawing existing meshes until replacements are ready. CPU meshing and opt-in capture file writes happen outside the frame thread. Upload budgets limit admission rather than guaranteeing a maximum driver-call duration. Renderer frame capture and deferred work are documented in [benchmarking.md](benchmarking.md).

Run `mise run bench` to record serial and four-region concurrent chunk generation, warm block reads, and durable edit latency. The JSON format and comparison command are documented in [benchmarking.md](benchmarking.md). This measures engine paths, not renderer frame time or a full-game speedup. Benchmark output is deliberately not a CI threshold because CPU topology and runner load vary.

The public Elixir character profile owns movement tuning. `Wyram.Character.State` owns position, velocity, jump eligibility and grounding. `Characters` stores dense bodies in one shared owner, with bounded native query batches and an ETS latest-snapshot slot; at most one notification waits in ClientPort. Native collision treats missing chunks as unavailable and checks complete feet-space AABBs with analytic axis sweeps. See [gameplay-plan.md](gameplay-plan.md) for subsequent postures, traversal and reusable presentation.

Continuous snapshot traffic can race with a closing client pipe. On Windows, a Rustler resource retains a read-only OS process handle before initialization, and the client-port owner polls it without waiting. This preserves the actual native exit status even when the port driver closes with EPIPE. Handles are released by the resource's OwnedHandle. The ordinary port exit-status path remains available.

Character model catalogs arrive with initialization, while bounded roster snapshots carry model IDs and approved posture/action state. The client caches rigs and replicas, retargets original procedural animation through semantic bone roles, and uploads one bounded character vertex batch. Rig evaluation cannot move authority. First/third/front camera placement uses only cached packed terrain and never changes the character head-origin edit ray.
